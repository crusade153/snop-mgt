# 주간 완제품 재고 요약장표 — 설계 확정본

> 대상: 사이드바 `일일 관리 (Morning)` 자리를 대체하는 신규 장표.
> 상태: **1차 구현 완료 · 검증 통과.** 개발 현황과 남은 일은 문서 끝 9절을 볼 것.
> 원본: `재고관리_마케팅&SCM_260810.xlsx` 의 `요약(0810)` 탭
> (CM×공장×카테고리 재고·출고·생산 + 소비기한 구간 + 이슈재고 소진). 직전 주차 `요약(0803)` 과 대조 완료.

## 0. 이 장표의 존재 이유

기존 대시보드는 **흐르는 재고를 붙잡지 못한다.** 매 조회마다 "지금" 재고만 계산할 뿐,
지난주 재고가 얼마였는지를 어디에도 남기지 않는다. 그래서 "전주 대비 13억 감소" 같은 문장을 만들 수 없다.

이 장표의 핵심은 화면이 아니라 **주 단위 적재**다. 화면은 적재된 값을 보여줄 뿐이다.

⚠️ **재고는 소급 생성이 불가능하다.** `V_MM_MCHB_ALL`·`MM_MCHB` 는 현재 시점의 배치 재고라서
지난 일요일 재고를 되돌려 만들 수 없다. 반면 **출고·생산은 전표 이력(`SD_ZASSDDV0020`, `MM_MB51`)이라 소급 계산이 된다.**
→ 적재를 켠 날부터 재고 열이 쌓이고, **첫 「전주 대비」는 2주 뒤에 나온다.**

## 1. 주차 정의 · 적재 시점 (확정)

| 항목 | 값 |
| --- | --- |
| 주차 | **월요일 ~ 일요일** |
| 재고 기준일 | **일요일 마감** (주차 종료일) |
| 주차 키 | 종료 일요일 날짜 (예: `2026-08-16`) |
| BigQuery 갱신 | 월요일 새벽 **04:00 KST** |
| 주간 적재 cron | **월요일 05:40 KST** = `40 20 * * 0` (UTC 기준, 일요일 20:40) |
| 출고·생산 집계 구간 | 해당 주 월요일 00:00 ~ 일요일 24:00 (`VDATU` / `BUDAT`) |

### 적재 개시 시점 (확정)

**서두르지 않는다.** 첫 주(개발 완료 직후 주차)는 **재고 열을 빈값으로 두고**,
그 다음 주부터 적재된 값으로 전주 대비 분석을 시작한다.
→ 화면은 처음부터 "데이터 없음" 상태를 정상적으로 그려야 한다. 빈 주차를 오류로 취급하지 말 것.

### 적재 규칙

- 적재는 **멱등(idempotent)**. 같은 주차를 다시 돌리면 upsert 로 덮어쓴다.
- 단, 재고 열은 다시 떠도 "그때의 재고"가 아니라 "지금 재고"가 들어온다.
  → **재고는 최초 1회만 쓰고 이후 갱신하지 않는다.** 출고·생산·매출만 재계산을 허용한다.
- 실패 대비로 관리자 화면에 **수동 적재 버튼**(주차 지정)을 둔다.
- Vercel **Pro 플랜**이므로 주 단위 cron·분 단위 스케줄을 그대로 쓸 수 있다.

⚠️ `vercel.json` 의 기존 일별 cron 은 `45 21 * * *` = **06:45 KST** 다(말씀하신 05:30 과 다름).
05:30 으로 옮기려면 `30 20 * * *` 로 바꿔야 한다. 주간 cron 은 `40 20 * * 0` 으로 추가해 두었다.

### 창고 스코프 — **고정** (구현: `lib/weekly/classification.ts`)

⚠️ **화면에 창고 그룹 필터를 두지 않는다.** 이 장표의 재고금액은 `/stock` 의 「통합 재고」와
**항상 같은 값이어야 한다.** 필터로 스코프가 흔들리면 두 화면 중 어느 쪽을 믿어야 할지 알 수 없게 된다.

| 그룹 | 포함 | 정의 |
| --- | --- | --- |
| `PLANT` 플랜트 | O | 사내 공장 저장위치 |
| `LOGISTICS` 물류 | O | FBH 물류센터 (`V_WMV_CST_INVNLIST`) |
| `OTHER` 기타 창고 | X | 2141·2143·2240·2243 매출이관/이월, 9000 오드그로서, 9100 미식마켓 |
| — 버림 | X | **3000 물류창고** — FBH 재고의 SAP 측 미러 |

- 기본 스코프는 `WEEKLY_DEFAULT_SCOPES = ['PLANT', 'LOGISTICS']` 하나로 정의돼 있다.
- `OTHER` 는 적재는 하되 화면 집계에서 빠진다. 나중에 보고 싶어지면 스코프만 넓히면 되고 재적재는 필요 없다.
- 대상 자재: 완제품·상품 대역 `50000000`~`69999999` 전부 — 판매용·자소용·상품 모두 포함.

**실측 스코프별 재고금액 (2026-08-23 주차)**

| 스코프 | 재고금액 | SKU |
| --- | ---: | ---: |
| 플랜트 | 120.9억 | 761 |
| 물류(FBH) | 5.4억 | 424 |
| **플랜트 + 물류 (화면 기준)** | **126.25억** | **1,167** |
| 기타 창고 | 3.3억 | 927 |

⚠️ **저장위치 3000(물류창고)은 어느 그룹에도 넣지 않는다.** 구현 중 실데이터로 확인한 결과 FBH 물류센터 재고의
SAP 측 미러였다. 실측: 3000 에 재고가 있는 445품목 중 **381품목이 FBH 에도 있고, 32품목은 수량까지 완전히 일치**한다
(3000 총 243,797 vs FBH 177,963). 기타창고에 넣었으면 물류 재고를 두 번 셌을 것이다.
나머지 제외창고는 FBH 와 겹치지 않는다(9100 은 446품목 중 16품목, 9000 은 317품목 중 1품목).

## 3. 단가 규칙 (확정 — 앱 전체 적용)

원가팀 `ending_inventory`(별도 Supabase) 단가만 쓴다.
**SAP 표준가(STPRS)는 금지** — 미사용 자재에 5천만원/EA 가 남아 금액이 30배 튄 전례가 있다.

**폴백 체인(신규):**

```
최신 as_of_month 단가  →  없으면 직전월  →  …  →  최대 6개월 역탐색  →  끝까지 없으면 빈값(금액 미산출)
```

- 역탐색 상한 **6개월** (그 이상 과거 단가는 현실성이 떨어져 금액을 만들지 않는 편이 낫다).
- **적용 범위: 앱 전체.** 주간 장표만이 아니라 `/stock`·MCP·아침브리핑·제품 상세 모두 같은 규칙을 쓴다. (확정)
- 어느 월 단가를 썼는지 기록한다. 구현은 `PriceSource` 유니온을 건드리지 않고 **`priceMonth` 를 따로 돌려주는 방식**을 택했다
  (유니온에 값을 추가하면 `/stock`·분석·스냅샷의 "금액이 있는가" 판정을 전부 손봐야 해서 위험이 컸다).
  주간 스냅샷은 `price_month` 컬럼에 그대로 남긴다.
- 실측(2026-08-16 주차): 2,072행이 최신월(202608), **17행이 202607, 9행이 202606 단가로 붙었고** 62행은 끝내 못 찾아 금액 0 이다.
- `as_of_month` 는 "그 달의 기초" = **전월 기말**이라는 기존 해석을 유지한다.

### 앱 전체 적용에 따라 함께 고쳐야 할 것

1. **`CLAUDE.md` 단가 규칙 문장** — "거기 없는 자재는 금액을 만들지 말고 `CURRENT_MONTH`(당월생산)로 표기한다" → 역탐색 규칙으로 교체.
2. **`PriceSource` 타입** (`lib/ending-inventory-price.ts:17`) — 적용월을 담도록 확장.
3. **캐시 키 버전업** (계산 결과가 바뀌므로 필수):

   | 파일 | 현재 키 | → |
   | --- | --- | --- |
   | `lib/ending-inventory-price.ts:134` | `ending-inventory-prices-v1` | `v2` (자료구조 자체가 바뀜) |
   | `actions/dashboard-actions.ts:209` | `dashboard-analysis-v8-ads-with-261-*` | `v9` |
   | `actions/inventory-actions.ts:37` | `inventory-status-v1` | `v2` |
   | `actions/product-actions.ts:195` | `product-detail-v1` | `v2` |

   자재 쪽(`material-facts-v4-*` 등)은 자재 대역 단가를 따로 쓰므로 영향 없다.

4. ⚠️ **이미 적재된 일별 스냅샷은 소급 변경되지 않는다.**
   `snop_inventory_daily_snapshots` 의 과거 행은 옛 단가 규칙으로 굳어 있으므로,
   규칙을 바꾼 **그날 아침브리핑의 「전일 대비」가 한 번 크게 튄다.** 그날은 안내 문구를 띄우거나
   과거 스냅샷을 재계산해 덮어써야 한다(재계산은 재고 수량이 남아 있으므로 단가만 다시 곱하면 가능).

## 4. 분류 규칙 — DISPO 기준 (확정)

CM 기준정보가 아직 없으므로 **당분간 DISPO 로 카테고리·공장을 판정**하고,
제품계층 4레벨이 BigQuery 에 올라오면 소스만 교체한다.

| 카테고리 | DISPO (뒤 두 자리) | 공장 | CM |
| --- | --- | --- | --- |
| 냉동 | 01, 02, 03, 04, 05, 10 | K1 | CM1 |
| HMI(조미) | 06, 07, 08, 09 | K1 | **CM2** |
| 즉석밥 | 30, 31, 32 | K2 | CM2 |
| 라면 | 11 ~ 17, 19 | K3 | CM3 |
| 상품 | H01 (H 접두 전체) | - | **상품** |
| 기타 | 그 외 전부 · DISPO 없음 | - | 미분류 |

- **접두 문자 M(생산)과 A(자소용)는 같은 표를 탄다.** A08 은 M08(소스)과 같은 라인이라 HMI 다. (확정)
  모르는 접두는 뒤 두 자리가 같아도 섞지 않고 기타로 남긴다 — 매핑 누락을 금액으로 드러내기 위한 것이다.
- **H01 은 상품**이다. 생산 CM(CM1~CM3) 어디에도 넣지 않고 `상품` 행으로 따로 합산한다(합계행에는 포함).
  `snop_cm_mapping` 은 CM1~CM3 만 담을 수 있으므로(체크 제약) 상품 판정은 매핑 테이블보다 앞선다.

- **M13(전처리) 는 라면(K3) 이 맞다** — 조직표상 K1 냉동팀_전처리와는 별개 판정이며, 이 표 기준이 우선한다. (확정)
- **HMI 는 CM2** 다. (확정)
- **M19(분말스프) 는 K3**, **M31(FD 동결건조) 는 K2** 다. (확정)
  - M31 은 품목 성격이 즉석밥이 아니라 **FD(동결건조)** 지만, 원본 장표의 카테고리 축이 4개(냉동·HMI·즉석밥·라면)뿐이라
    당분간 K2 의 `즉석밥` 행에 함께 잡힌다. **FD 를 별도 카테고리 행으로 떼는 것은 언제든 가능하다** —
    적재 단위가 SKU 이고 `dispo` 원본값을 그대로 보관하므로, 카테고리 매핑 한 줄만 고치면 **과거 주차까지 전부 다시 접힌다.**

참고 — 현재 코드(`lib/inventory-classification.ts`)의 DISPO 라벨:

```
M01 냉동밥    M02 오니기리   M03 냉동만두   M04 튀김      M05 핫도그
M06 추출/농축  M07 HMI       M08 소스      M09 분말      M10 냉장만두
M11 건면봉지   M12 유탕봉지   M13 전처리     M14 건면컵     M15 유탕컵
M16 요리면봉지 M17 요리면컵   M19 분말스프
M30 즉석밥1   M31 FD        M32 즉석밥2
```

### CM1 / CM2 / CM3

- **SKU → CM 매핑 테이블을 Supabase 에 둔다**: `snop_cm_mapping (material_code, cm_code, valid_from, updated_by)`.
- 관리자 화면에서 CSV/시트 업로드로 채운다. 기준정보 확정 전에도 개발·검증을 끝낼 수 있다.
- 매핑이 없는 SKU 는 위 표의 **DISPO → CM 기본값**으로 떨어뜨리고, 그것도 없으면 `미분류` 행으로 노출한다.
  **미분류를 숨기지 않는다** — 매핑 누락을 금액으로 즉시 드러내기 위한 것이다.
- 제품계층 4레벨이 BigQuery 에 올라오면 이 테이블을 소스에서 걷어내고 PRDHA_4 로 갈아끼운다(화면·집계 로직은 그대로).
  현재 앱이 읽는 것은 `PRDHA_1_T / 2_T / 3_T` 까지다.

## 5. 지표 정의 (확정)

| 열 | 정의 |
| --- | --- |
| 전주 재고 | 직전 주차 스냅샷의 재고금액 |
| 주간 출고 | 해당 주 `SD_ZASSDDV0020` 납품 수량 × **원가단가** (VDATU 기준) |
| 주간 생산 | 해당 주 `MM_MB51` BWART 101 − 102 수량 × **원가단가** (BOX 는 `SD_MARA.UMREZ_BOX` 로 EA 환산) |
| 당주 재고 | 해당 주차 스냅샷의 재고금액 |
| 소비기한 구간 | 잔여율 5구간 — `~50%` / `50~70%` / `70~75%` / `75~85%` / `85%~`. **기존 `lib/inventory-board.ts:191` 로직 그대로 재사용** |
| 월매출 비 재고금액 | 당주 재고금액 ÷ **당월 납품매출 실적 누계** (`SUM(NETWR)`, VDATU, 당월 1일~기준일) |

**단가 기준 통일(확정): 재고·출고·생산 세 열 모두 `ending_inventory` 원가단가를 쓴다.**
납품매출액(`NETWR`)은 「월매출 비」의 **분모 전용**이며, 출고 금액과 섞지 않는다.

⚠️ **품질대기(CINSM)는 재고에 넣지 않는다.** `/stock` 의 「재고금액」이 가용재고(CLABS)만 세기 때문이다.
초기 구현이 `CLABS + CINSM` 을 더해 두 화면이 137.2억 vs 126.3억으로 어긋났다. 쿼리 단계에서 `CLABS > 0` 으로 막는다.

### 소비기한 구간별 주간 재고변동 표 (확정)

원본 엑셀에서 이 표의 합계(9,382,623,247)가 상단 표 합계(8,076,220,692)와 어긋나는데, **이는 수기 시트의 계산오류다.**
상단은 팀별로 찢은 것, 하단은 합친 것이라 **원래 같은 값이 나와야 한다.**

→ 웹에서는 두 표를 **같은 원천(주간 스냅샷)에서 뽑아** 합계가 구조적으로 일치하게 만든다. 수기 시트의 갭은 재현하지 않는다.

표 구성(원본과 동일):

| 행 | 값 |
| --- | --- |
| `{전주 종료일} 재고` | 전주 스냅샷의 구간별 재고금액 |
| `전주 比 증감액` | 당주 구간액 − 전주 구간액 |
| `전주 比 증감률` | 증감액 ÷ 전주 구간액 |

⚠️ 원본 `요약(0810)` 의 이 행은 `8/3 재고` 로 적혀 있으나 값은 **7/26(전주) 재고**다. 라벨도 수기 오류이므로
웹에서는 **주차에서 자동 생성**한다(합계 행이 `8/9 합계` 로 잘못 박힌 것도 같은 원인).

### 대차(對査) 검증

`전주 재고 + 주간 생산 − 주간 출고` 와 `당주 재고` 는 **정확히 맞지 않는다.**

원본 엑셀 실측: `9,336,548,488 + 1,185,887,135 − 2,159,392,381 = 8,363,043,242` vs 실제 `8,076,220,692`
→ **갭 286,822,550원 (3.4%)**. 폐기·반품·재평가·단가 변경·창고 스코프 차이가 섞인 것으로 보인다.

→ 세 열을 각각 독립 집계로 두되, **갭을 숨기지 말고 「차이」 열로 표기**한다. 갭이 급증하면 그 자체가 이상 신호다.

(참고: 원본의 「월매출 비」는 검산이 맞는다. CM별 분모를 역산해 합치면 5,373,956,553 이고
8,076,220,692 ÷ 5,373,956,553 = 150.3% 로 합계 151% 와 정합한다.)

## 6. 저장 구조 — **SKU 단위로 적재한다**

⚠️ **집계 행(CM×공장×카테고리)으로 적재하면 안 된다.**
CM 매핑이 아직 확정 전이고 제품계층 4레벨로 교체될 예정인데,
집계해서 저장해 버리면 **매핑이 바뀌었을 때 이미 쌓인 과거 주차를 다시 쪼갤 수 없다.**
SKU 단위로 남겨 두면 매핑만 고쳐 과거 주차를 통째로 재집계할 수 있다.

행 수도 문제되지 않는다 — 재고 보유 완제품이 약 750품목이므로 **주당 750~3,000행, 연 15만행 수준**이다.
(비교: 기존 일별 스냅샷은 같은 품목을 매일 쌓아 연 27만행이며 이미 잘 돌고 있다.)

```
snop_weekly_inventory_snapshots
  week_end_date    date      -- 주차 종료 일요일        (PK)
  material_code    text      -- SKU                     (PK)
  storage_scope    text      -- PLANT / LOGISTICS / OTHER (PK)

  product_name     text
  dispo            text      -- 분류의 원천. 집계는 조회 시점에 이 값으로 접는다
  plant            text      -- K1/K2/K3/기타 (dispo 파생, 조회 편의용 비정규화)
  category         text      -- 냉동/HMI/즉석밥/라면/기타 (dispo 파생)
  unit             text

  stock_qty        numeric
  stock_value      numeric   -- 원가단가 기준 재고금액
  bucket_under50   numeric   -- 잔여율 구간별 재고금액 5열
  bucket_50_70     numeric
  bucket_70_75     numeric
  bucket_75_85     numeric
  bucket_85_over   numeric

  shipped_qty      numeric   -- 주간 출고 (VDATU)
  shipped_value    numeric   -- 원가단가 환산
  produced_qty     numeric   -- 주간 생산 (MB51 101-102)
  produced_value   numeric   -- 원가단가 환산
  sales_amount     numeric   -- 해당 주 납품매출액(NETWR) — 월매출 비 분자 누적용

  unit_price       numeric
  price_month      text      -- 실제 적용된 단가 기준월 (예: 202606)
  price_source     text      -- ENDING_INVENTORY / FALLBACK / NONE
  created_at       timestamptz
```

- **CM 코드는 이 테이블에 넣지 않는다.** `snop_cm_mapping` 과 조회 시점에 조인한다 — 매핑이 바뀌면 과거도 같이 따라오게 하기 위한 것이다.
- RLS 는 기존 일별 스냅샷과 동일하게 **service_role 전용**, `anon`/`authenticated` 권한 회수.
- 스키마는 `supabase/weekly-summary-board.sql` 로 남기고 대시보드에서 수동 실행한다(이 저장소는 마이그레이션 러너가 없다).
- 조회는 Supabase 집계 뷰 또는 서버 액션에서 접는다. **BigQuery 를 다시 때리지 않는다** — 적재 이후 이 장표는 BigQuery 비용이 0 이다.

### 비고란 문구

```
snop_weekly_board_notes (week_end_date, section, body, updated_by, updated_at)
```

**템플릿 자동 생성 + 관리자 수동 오버라이드** 병행 — 예) `전체 재고금액은 전주 대비 {n}억 {증가|감소}`.
자동 문구는 매주 값만 갈리고, 관리자가 고치면 그 주차는 수정본이 우선한다.

### 월 출고 比 재고금액 (2026-08 변경)

분모를 **매출액(NETWR) → 당월 누적 출고금액(원가단가 환산)** 으로 바꿨다.
분자인 재고금액은 원가인데 분모가 판매가여서, 마진율만큼 비율이 눌려 "몇 주치 재고인가"로 읽을 수 없었다.

- 주간 출고금액·누적 출고금액·생산금액·재고금액이 **전부 같은 단가**(원가팀 기말재고 단가)다.
- 누적 출고는 주간 출고와 같은 기준(`SD_ZASSDDV0020`, VDATU, BOX→기본단위 환산)이며 기간만 당월 1일~주차 종료일이다.
- 적재 열이 `shipped_mtd_qty` / `shipped_mtd_value` 로 늘었다. **`supabase/weekly-summary-board.sql` 의 4절 ALTER 를 먼저 실행해야 적재가 된다.**
- NETWR 은 `sales_amount`·`sales_mtd` 로 계속 적재하지만 비율에는 쓰지 않는다(실매출 참고용).

### 남은 일 ② — 이슈재고 소진 구글시트 (8절)

시트 URL·탭·컬럼 구조·"이슈재고" 정의·서비스계정 공유가 필요하다. 화면에는 아직 자리도 잡지 않았다.

### 운영 메모

1. **Supabase 스키마는 실행 완료**(`supabase/weekly-summary-board.sql`).
2. 첫 적재는 화면의 **적재 버튼**을 쓴다. cron 은 매주 월요일 05:40 KST 에 직전 주차를 적재한다.
   - 진행 중인 주차도 적재할 수 있고, 이때는 **잠정치**라 누를 때마다 재고까지 갱신된다.
   - 마감된 주차는 재고를 다시 쓰지 않고 출고·생산·매출만 갱신한다.
3. ⚠️ **적재는 반드시 서버 액션(적재 버튼)이나 cron 으로 한다.** 스크립트로 DB 를 직접 고치면
   `unstable_cache` 가 옛 집계를 최대 10분 들고 있어 화면 숫자가 어긋난다(실제로 137.2억이 떴던 원인).
4. 단가 역탐색이 앱 전체에 적용되므로 **배포 직후 아침브리핑의 「전일 대비」가 한 번 튄다**(3절 4항).

### 확정된 운영 기준

- **노출**: 로그인 사용자 전원 / **적재는 관리자만**
- **보존**: 영구 보관(DB)
- **과거 백필**: 하지 않는다
- **금액 표기**: 화면은 백만원·원 토글, 비고 문구는 1억 이상 `n.n억` / 그 미만 만원 단위
- **이슈재고 4열**: 상단 표에서 빼고 별도 섹션으로 둔다
